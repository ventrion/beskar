# Babysit a pull request

A PR is not a task, it is an artifact that lives for days: reviewers comment, the target branch moves underneath it, CI runs fail, and the issue tracker quietly stops reflecting reality. Babysitting drives it towards one state:

**Every thread answered, CI green, branch current, title and description accurate, issue tracker updated.**

Each invocation drives the PR as far as it can right now, then stops and reports. It never waits for CI and never sits watching. The user runs it again when there is something new to react to.

## Prerequisites

Requires the GitHub CLI (`gh`) installed and logged in (`gh auth status`). If `gh` is missing or unauthenticated, stop and instruct the user to install `gh` or run `gh auth login`.

## 1. Resolve the target

From `#123`, a PR URL, a branch name, or "my PR" (queried via `gh pr view` or `gh pr list --author "@me"`), establish:
- The GitHub repository (`owner/repo`), PR number, head branch, and base branch.
- The linked work item:
  - A Rohrpost ticket id (such as `RP-a1b2c3` or `a1b2c3`) from the branch name, PR title, or description body (`Fixes RP-a1b2c3`, `Refs RP-a1b2c3`, or `rp` links).
  - A GitHub issue number (such as `#42` or `42`) from the branch name, PR title, or description body keywords (`Fixes #42`, `Closes #42`, `Refs #42`).
  - Whether the repository tracks work in Rohrpost (`.rohrpost/` directory) or GitHub Issues.

State what you resolved before touching anything. A wrong target caught here costs nothing.

Done when: you hold repository, PR number, both branch names, and either a linked Rohrpost or GitHub issue identifier or an explicit "no ticket linked".

## 2. Assess, and report before acting

Take the snapshot first:

- Open review threads and comments from `gh pr view <number> --comments` and `gh pr view <number> --json reviewDecision,reviews,comments`, split into those awaiting a reply from your side and those already answered.
- CI check status of the latest commit (`gh pr checks <number>` or `gh run list --branch <branch>`), and which checks failed.
- Commits behind the base branch (`git fetch origin`, then compare divergence between head and base).
- Linked issue state:
  - For Rohrpost: `rp show <id> --json` (status: `open`, `in_progress`, `review`, `done`, `waiting`).
  - For GitHub Issues: `gh issue view <id> --json state,labels,title`.
- Title and description, against `.github/pull_request_template.md` (or `.github/PULL_REQUEST_TEMPLATE/`) and repository conventions.

Hand the user this snapshot before changing anything. It is the checkpoint where they redirect you.

Done when: the user has the snapshot and you know which of the five areas need work.

## 3. Answer the review comments

Reply, and leave the thread open. Its creator resolves it. That holds even when the fix is obvious and already pushed. Your reply says what changed and points at the commit. The decision that it is settled belongs to whoever raised it.

Sort every open thread into three piles:

- **Mechanical**: a named change with one obvious correct implementation: a rename, an extracted function, a missing null check, a typo, an absent test case. Implement the fix, commit, and reply with the commit reference.
- **Substantive**: questions the design, disputes the approach, asks why, or leaves you guessing at intent. Draft the reply and surface it to the user before posting.
- **Already satisfied**: a later commit already handled it. Reply pointing at that commit.

Post replies using `gh pr review <number> --comment -b "..."` or GitHub API review thread reply endpoints (`gh api repos/{owner}/{repo}/pulls/{number}/comments/{comment_id}/replies -f body="..."` or GraphQL `addPullRequestReviewThreadReply`).

Commit so the mapping is visible: one commit per thread, or one commit naming the threads it answers. The reviewer re-reads the diff faster when commits line up with comments.

Mark agent-authored replies according to team convention (such as leading with `> *This reply was generated by AI.*`).

Done when: every open thread carries a reply, or a drafted reply awaiting the user, and you can name which is which.

## 4. Clear red CI runs

Pull the failed checks for the head commit using `gh pr checks <number>` or `gh run list --branch <branch>`. Read the failed run logs with `gh run view <run-id> --log-failed` before touching anything. Search the log (`… --log-failed | rg -i 'fail|error'`) instead of reading its tail — the failing gate often sits earlier than the end-of-run summary. Sort each failure:

- **Real**: your code or your test broke it. Fix the root cause. Never weaken an assertion, skip a test, or loosen a lint rule to reach green.
- **Flake**: non-deterministic, unrelated to the diff, passes on rerun. Retry the job with `gh run rerun <run-id> --failed`. State that you did, and state which job.
- **Infrastructure**: runner, network, credentials, registry. Report it with the log snippet.
- **Pre-existing**: the base branch is red too. Report it and move on.
- **Blocked**: the run is in `waiting` with no started steps — a deployment-environment approval gate, not a failure.

When the repository has local test or lint commands, run it after your changes and before pushing. A local run costs seconds; a CI cycle costs minutes.

Done when: every failed check is classified, real failures are fixed at the cause, and anything you are not fixing is reported with its reason.

## 5. Sync with the target branch

Only when the PR branch is behind the base branch.

Follow the repository convention (rebase or merge), read from the repository rather than assumed. Confirm with the user before rewriting history, and push with `--force-with-lease`.

Two stop conditions:

- **Someone else has commits on the source branch.** Stop and ask. Rebasing a shared branch destroys their work.
- **Conflicts.** Hand off to the `resolving-merge-conflicts` skill rather than improvising.

Push once, after comment fixes, CI fixes, and branch sync are all complete.

Done when: the source branch carries the target's latest commits and is pushed, or the user declined, or conflicts were handed off.

## 6. Polish title and description

Read the project's template from `.github/pull_request_template.md` or `.github/PULL_REQUEST_TEMPLATE/`. Derive the title convention from the last handful of merged PRs in the repository (`gh pr list --state merged --limit 5 --json title`) rather than guessing.

The description says what changed and why, links the issue, and names anything the reviewer needs to know before reading the diff. Update the PR using `gh pr edit <number> --title "..." --body "..."`.

Done when: the title matches the observed convention, the description follows the template, and the issue link is present.

## 7. Update the linked issue

Update the linked ticket or issue state:

- **Rohrpost (`rp`)**:
  - When the PR is ready for review, set the status to `review`: `<rohrpost-skill>/scripts/rohrpost set <id> status=review --json`.
  - Add a progress note: `<rohrpost-skill>/scripts/rohrpost comment <id> "Updated PR #123 with latest review fixes" --json`.
  - When the PR is merged, close the ticket: `<rohrpost-skill>/scripts/rohrpost close <id> --reason "Merged in PR #123" --json`.
- **GitHub Issues (`gh issue`)**:
  - Ensure the PR description links the issue with closing keywords (`Fixes #<id>`, `Closes #<id>`) or reference keywords (`Refs #<id>`).
  - Update labels if the repository tracks triage roles or workflow states with labels (`gh issue edit <id> --add-label "..."`).
  - Add a progress comment if needed: `gh issue comment <id> --body "..."`.

Done when: the issue state matches the PR status, the PR is linked, and a comment or event records the update.

## 8. Stop and report

Close every invocation with:

- What changed: commits pushed, threads answered, CI runs retried, fields updated.
- What is blocked on the user: substantive replies drafted, rebase awaiting confirmation, infrastructure failures, design decisions.
- What is blocked on a reviewer: threads you answered that only their creator can resolve.
- What the next invocation picks up: the CI run you did not wait for, named by run id or check name.

Done when: the user knows the PR's current state, their own next action, and yours.

## Configuration this expects

Per repo or per team:

- GitHub CLI (`gh`) installed and authenticated.
- Target issue tracker: Rohrpost (`.rohrpost/` with `rp`) or GitHub Issues (`gh issue`).
- Rebase or merge for keeping up with the target branch.
- PR state to issue state mapping.
- How agent-authored comments are marked.
