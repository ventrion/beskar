# One lock, short transactions, and recovery instead of a journal

Several agents and a person can run Beskar at the same time, and any of them can be killed halfway. Every change to the library, the registry or a workspace's skills therefore happens inside a transaction, `Beskar::transact`. It takes the operating-system lock in Beskar's home, cleans up leftovers of interrupted runs, reads the registry fresh, makes the change, and saves the registry only if it changed. Reading under the lock means no process overwrites another's registry changes. The kernel releases the lock when a process dies, so a crash never leaves Beskar locked.

Transactions are short. `update --all` takes one transaction per workspace, and a person deciding a conflict is asked before the lock is taken. Under the lock Beskar plans again, and a decision counts only if the skill still has the same library version, base, declined version and workspace copy it was made for. Otherwise the person is asked again. A waiting process says who it waits for, and gives up after `lock-timeout` seconds: 60 by default, or what `BESKAR_LOCK_TIMEOUT` says.

File changes are renames of whole directories. A copy is assembled in a `.beskar` work directory inside the skills directory, the old copy is moved aside there, checked once more against the fingerprint the plan saw, and only then replaced or deleted. Each temporary name says what it was for, which skill it stands in for and which process made it, so recovery can finish or undo the step without a record of its own: an old copy whose replacement never arrived goes back, one whose replacement is in place is deleted, entries carried into an unfinished staging copy return to their skill, and whatever else is left is deleted unless it holds files that are not part of a skill. A registry that was not saved after a crash is harmless too, because three-way planning adopts copies that match the library and reinstalls copies that are missing.

## Considered options

- **An undo journal**, as one competing implementation has. A complete record of every step makes any crash reversible, but it is a second format to write, sync and recover, and it forces all-or-nothing batches across workspaces. The rename steps and self-healing planning already cover every crash point we could produce, without it.
- **Locking only the registry write, with file changes unlocked**, as another competing implementation does. Shorter waits, but two processes could then replace the same skill at once; per-skill re-checks narrow that window without closing it.
- **Holding one lock for a whole `update --all`, prompts included**, the first design. Simple, but one person thinking about a conflict made every agent on the machine fail after the fixed ten-second wait.
