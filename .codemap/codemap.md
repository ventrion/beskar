## Worst offenders

- **Git backend (57/D)** — crates/beskar-git/src/lib.rs:44-59: `redact_url` only works when the whole string IS a URL, yet `git_failure` (706-713) and `network_failure` (736) apply it per stderr line. For a real line like `fatal: unable to access 'https://user:pw@host/r.git/': ...` the `://` sits far past index 9, so control falls to the scp arm, where `url[..at]` contains '/' and the line is returned UNCHANGED — credentials are not redacted. Conversely for scp-form lines like `error: failed to push some refs to 'git@github.com:org/repo.git'` the arm returns `url[at+1..]`, TRUNCATING the message to `github.com:org/repo.git'`. The module header and trait docs promise 'credential-bearing URLs are redacted from every error' (§67 MUST); the control is a no-op for the exact input shape it receives and corrupts common messages. Tests (875-897) exercise only bare URLs; no test feeds a stderr line. Actual leakage today mostly relies on git's own `transport_anonymize_url`, not on this code.
- **Legacy migration (62/C)** — crates/beskar-core/src/migrate.rs:869-955: `validate_skills_working_tree` is a near line-for-line copy of the private `scan_skills_dir` (library.rs:396-482) plus an inlined copy of `reject_nested_roots` (library.rs:380-393): same WalkDir loop, same symlink/special-object/`SKILL.md directly inside` checks, same `split_leaf`/`validate_bucket`/frontmatter/leaf-equality/duplicate-name sequence. The doc comment even says it validates 'exactly as a Beskar library scan will'. Drift has already begun (migrate's messages append '(§12)'/'(§11)'; library's duplicate message names both paths). The owner is library.rs; `scan_skills_dir` should be exposed `pub(crate)` and reused — `Library::scan` can't be called only because `beskar.toml` doesn't exist yet, which is not a reason to fork the rules.
- **GUI service bridge (64/C)** — crates/beskar-gui/src/services.rs:81: The GUI bridge is a near-verbatim sibling copy of crates/beskar-tui/src/service.rs (~840 LoC) fulfilling the same actions against the same core services: `to_native` is byte-identical, `owners` identical modulo a type path, `load_membership` near-verbatim (including the same `SkillName::parse(skill).ok()` idiom), and `gather`/`load_skill`/`install_change`/`library_change`/`reorder_change`/`update_all_lines`/`operation_outcome`/`library_outcome` all mirror the TUI versions. They have already drifted: GUI `update_all_lines` emits a 'nothing to do — every installation is up to date' line the TUI version lacks. No shared abstraction covers this; ~1,100 LoC must evolve in lockstep in two places.
- **Library (64/C)** — crates/beskar-core/src/library.rs:278-374: Two parallel skill-validation pipelines in one file: `resolve_skills` (git tree entries) and `scan_skills_dir` (lines 396-482, walkdir) each re-implement the same rule set — locate SKILL.md roots, reject SKILL.md directly under skills_dir, `reject_nested_roots`, `split_leaf`+`strip_prefix("{skills_dir}/").unwrap_or_default()`+`validate_bucket`, leaf==frontmatter.name, duplicate-name rejection — with slightly divergent error texts (326 vs 451, 331-336 vs 465-470, 368-373 vs 475-481). Profile uniqueness (id + case-folded name) is likewise implemented twice: 224-249 (git) and 511-530 (fs). A source-agnostic core over an `(path, bytes)` entry list would collapse both.
- **Library init (72/C)** — crates/beskar-core/src/init.rs:166: `let head = backend.resolve_ref(dir, "HEAD").ok();` (and identically at init.rs:181 in adopt_library) swallows any Git error into `head: None`. The field doc at init.rs:65-67 states an adopted or cloned Library always has one, and the module doc (init.rs:12-14) promises every flow fails closed — so a `None` here can only be a swallowed failure (git missing, not a repo, unborn HEAD) that the caller cannot distinguish from a legitimate absence. Doc and code disagree; either propagate the error or document that `None` means HEAD unresolvable.
- **Installation lifecycle (74/C)** — crates/beskar-core/src/lifecycle.rs:1236: `fn upsert(registry, installation)` (find-by-id-then-replace, else `registry.insert`) is copy-pasted verbatim in registry_service.rs:546, whose doc comment even admits it 'mirrors the lifecycle upsert'. `Registry` in registry.rs already owns `find`/`insert`; this belongs there as `Registry::upsert`. Duplication with a clear owner.
- **Doctor (77/B)** — crates/beskar-core/src/doctor.rs:157: check_configuration calls std::fs::create_dir_all(&dirs.data_dir), violating the module's own contract that doctor is read-only and 'No check mutates anything' (examine doc, ~line 78). On failure it reports 'data directory ... is not writable: {err}', mislabeling any mkdir failure (path-is-file, parent permissions) as a writability problem — a diagnostics tool misclassifying its own finding and side-effecting the filesystem.
- **TUI service bridge (79/B)** — crates/beskar-tui/src/service.rs:241-527: plan() and execute() (fn at :241 and :527) are twin ~220-line exhaustive matches over the same 18 PendingAction variants; every request struct (AddRequest, DetachRequest, IngestRequest, PushRequest, ...) is rebuilt field-for-field in both arms with only `dry_run: true` flipped to `false`. Adding/altering an action means editing two parallel dispatches in lockstep; the compiler catches missing arms but not field drift between the plan and execute copies. A shared request-building step parameterized on dry_run (the flag the core services already expose) would remove most of the mirror, though the divergent result mapping (PlannedChange vs ActionOutcome) and branch ops without dry-run support justify some of the split.
- **GUI state (80/B)** — crates/beskar-gui/src/state.rs:1256: silent-except: `rank: values[0].parse::<i64>().ok()` — a non-numeric rank (e.g. "abc") silently parses to None, which the SkillRank semantics treat as 'clear the rank' (comment: 'a blank rank clears the rank'); the user gets no error and their existing rank is wiped. - **CLI grammar & dispatch (82/B)** — crates/beskar-cli/src/main.rs:216-219: Dead flag: `--prune` is defined in the grammar with a doc comment admitting "this changes nothing" and is bound as `prune: _` in dispatch (line 1121), never read. ## Cross-cutting themes

- **Credential redaction at the Git boundary is a no-op for real input.** The one HIGH in the repo: `redact_url` (beskar-git/lib.rs:44-59) handles a bare URL, but `git_failure`/`network_failure` feed it whole stderr lines. For `fatal: unable to access 'https://user:pw@host/r.git/': ...` the line is returned unchanged (credentials survive); for scp-form lines it truncates the message. The module header promises §67 redaction 'from every error' and the tests only cover bare URLs. Today leakage is prevented mostly by git's own transport_anonymize_url, not by this code. Fix is small: scan the line for URL tokens and redact each, then add a stderr-line test.
- **Silent degradation, now traced to its source.** 11 of 25 modules carry silent-except and 10 carry fallback. The re-audit shows most of them inherit from GitBackend: `remote_url` and `discover_repo` collapse every non-zero exit (not-a-repo, dubious ownership, corrupt config) into `Ok(None)`, `last_commit_info` turns a parse failure into 'no commit ever touched this path', and `parse_ls_tree` yields empty mode/oid instead of an error. Callers then add a second layer — init and lifecycle `.ok()` the HEAD lookup so a plain directory with a beskar.toml adopts as a Library with `head: None`; migrate writes the tip commit as `skill_commit` in a stamp it calls 'fully verified'. Making the backend distinguish 'absent' from 'failed' by exit code collapses most of the downstream findings at once.
- **The skill-scan rules exist three times, with one obvious owner.** library.rs `scan_skills_dir` + `reject_nested_roots` (private) are re-implemented near line-for-line by migrate.rs `validate_skills_working_tree` (doc: 'exactly as a Beskar library scan will') and again, in tolerant form, by editing.rs `collect_skill_names_tolerant`. Error texts have already drifted (§ references appended in one copy, both paths named in another). Inside library.rs itself the git-tree and working-tree pipelines duplicate the same rules with divergent messages, and profile uniqueness is checked twice. migrate's `find_committed_skill` is a weaker fork of `resolve_skills` and `detect_workspace_info` copies `WorkspaceInfo::capture`. Expose one source-agnostic scan core from library.rs and delete the forks — this single extraction is what drags library, migrate and lifecycle from B to C.
- **Spec contracts (§12, §26, §67) are enforced on one path and skipped on the sibling.** Symlink rejection runs on the working tree but a committed `120000` blob passes `resolve_skills` and is materialized as a regular file holding the link target. `beskar.toml` `skills_dir`/`profiles_dir` are joined onto the root unvalidated although `paths::validate_relative_path` exists, so cloned remote config can escape the Library. migrate's §26 pre-write check compares targets exactly while `Registry::insert` is case-insensitive, so a collision can surface in execute step 5 after the library commit and stamps are already written. `push_branch` passes the bare branch as refspec, so a leading '+' would force-push despite the 'never forces' doc. Each is a one-path gap: the correct rule already exists on the other path.
- **The TUI and GUI bridges are still twins.** Unchanged since the last run and still the largest single refactor: beskar-gui/services.rs mirrors beskar-tui/service.rs (~1,100 LoC, `to_native` byte-identical), both repeat plan/execute dispatch differing only in dry_run, and they have drifted (GUI drops rank validation the TUI performs). gui_services (64 C) is the only shell-layer C. Build each request once, parameterized by dry_run, and hoist mapping/validation into beskar-core.
- **The domain model and TUI runtime remain the reference points.** core_model (95 A) and tui_app (92 A) are unchanged and clean; reconcile, editing, status, registry, remote, platform and the four GUI/TUI view-layer modules sit at 82-88 B with only LOW findings. The new release_tooling module lands at 86 B: version bumping and packaging fail closed on every checked path, with the target list duplicated between release.py and release.yml and the unittest suite run twice on the same OS as its only debts. Fail-closed parsing of stamps, frontmatter and profile schemas, and plan-then-confirm-then-execute, are honored everywhere the auditors looked.
- **Oversized units: two are now worth splitting.** reduce.rs (2,497), state.rs (2,531), cli main.rs (2,301) and editing.rs (1,974) remain cohesive and sectioned. But migrate's `build_plan` (~340 lines, six phases, none independently testable) and beskar-git's 24 copies of the run/check-status/git_failure block (~90 lines that a `run_git_ok` helper would remove, and the one place to pin `LC_ALL=C` so auth classification stops depending on an English locale) have crossed from 'long' into 'hiding bugs'. Split those two first.
